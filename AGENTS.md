# Project maintenance notes

## Animation backend dependency lock

`backend/requirements.lock` pins the Windows CPython 3.11 dependencies for the ComfyUI animation backend. It includes PyTorch and torchvision CUDA 13.0 wheels; the image environment uses a separate CUDA 12.8 PyTorch wheel. Backend source revisions and installation are in `scripts/setup-animation.ps1`.

When changing a backend revision or dependency, update the lock, run `uv pip check`, and smoke-test the runtime. The setup script checks dependency compatibility before writing its readiness marker.

## Animation compatibility investigation

This document records the original compatibility investigation and memory failures. A subsequent five-frame mapped Q2/Q3 run completed on the RTX 4070 SUPER; see [the verification report](#verification-report) for its settings, measurements and visual limitations.

The supplied [adapter](https://huggingface.co/styly-agents/Wan2-2-pixel-animate/tree/be894a86acd595f6a1b414796b0b2bfecc793872) is for Wan2.2 **I2V-A14B**, which has separate high-noise and low-noise 14B experts. It is not the incompatible 5B TI2V model or the separately named Wan Animate model. The adapter repository is pinned at `be894a86acd595f6a1b414796b0b2bfecc793872`. Its `wan2-2-video.json` workflow applies the *same* pixel adapter at weight 1 to each expert. High noise runs denoising steps 0–2 and low noise runs 2–4; each has a separate 4-step distillation LoRA. The workflow uses DDIM/simple, four steps, CFG 1, shift 5, 45 frames, the Wan 2.1 VAE and UMT5 encoder. It uses `PainterI2V`, from `princepainter/ComfyUI-PainterI2V` at `714044a6536ad37293f0658e247c5c6be1622745`, with motion amplitude 1.1. The model card's automatically generated Diffusers snippet should not be treated as proof of compatibility.

The safetensors header was read using HTTP byte ranges, without downloading model bodies. The adapter contains 800 BF16 tensors: 400 A/B pairs, rank 256, covering 40 transformer blocks and self-attention q/k/v/o, cross-attention q/k/v/o and feed-forward 0/2. The adapter keys have `diffusion_model.blocks.N...lora_A.weight` / `lora_B.weight` format. Against both FP8 expert safetensors headers in `Comfy-Org/Wan_2.2_ComfyUI_Repackaged` revision `ee6f4a40737a995bf5818954cfce6d59443b0f04`, all 400 pairs per expert have a corresponding weight with matching matrix dimensions. This verifies static key and shape coverage only; it does **not** prove the runtime actually applied the patches. ComfyUI's generic LoRA loader recognizes `diffusion_model.*` and `.lora_A/B.weight` keys. A real backend must inspect the patch count and unmatched keys for *each* expert and refuse a job if coverage is incomplete.

A lower-memory candidate is [bullerwins/Wan2.2-I2V-A14B-GGUF](https://huggingface.co/bullerwins/Wan2.2-I2V-A14B-GGUF/tree/c95ab6c210a60ff915aa3f7cb0fa07300b0b2f36) revision `c95ab6c210a60ff915aa3f7cb0fa07300b0b2f36`, with high/low Q3_K_S experts (6,515,012,096 bytes each), loaded with [ComfyUI-GGUF](https://github.com/city96/ComfyUI-GGUF) at `6ea2651e7df66d7585f6ffee804b20e92fb38b8a`. That project's documentation explicitly calls LoRA loading experimental, and its patcher has code comments warning of possible out-of-memory during low-VRAM mmap release. The original Q3/FP8 candidate was not validated end to end. A later Q2/Q3 mapped run completed with both pixel-adapter coverage reports; see the verification report. A bounded 2 MiB header read of each pinned Q3 GGUF expert was also inspected with `scripts/inspect_gguf_headers.py`: each header lists 1,095 tensors, and all 400 adapter target names and logical shapes match in each expert. This does not validate tensor payloads or prove that ComfyUI applies the patches; runtime coverage and a meaningful generated result remain necessary.

With Q3_K_S experts (13.03 GB), FP8 UMT5 (6.74 GB), Wan 2.1 VAE (0.25 GB), two 4-step LoRAs (2.45 GB), and pixel adapter (2.45 GB), selected downloads total about 24.9 GB decimal, excluding runtime, cache overhead and temporary files. At investigation time, the machine had approximately 16.8 GiB free physical memory and 8.9 GiB free virtual/commit memory; actual availability changes. This does not prove failure: memory mapping, GPU offload, and sequential execution affect peak commit. It does mean blindly loading the full set can page or fail and is not a safe basis for claiming the 32 GB host works. Native Wan's own unquantized I2V example specifies at least 80 GB of VRAM. The later Q2/Q3 mapped route was tested in an isolated, memory-monitored run with adapter coverage verification; memory headroom remains important.

Sources: [adapter card and workflow](https://huggingface.co/styly-agents/Wan2-2-pixel-animate/tree/be894a86acd595f6a1b414796b0b2bfecc793872), [official Wan2.2 I2V](https://huggingface.co/Wan-AI/Wan2.2-I2V-A14B), [ComfyUI Wan2.2 guide](https://docs.comfy.org/tutorials/video/wan/wan2_2), [ComfyUI-GGUF](https://github.com/city96/ComfyUI-GGUF), and [PainterI2V](https://github.com/princepainter/ComfyUI-PainterI2V).

### Measured memory limit and explicit text-encoder alternative

On 2026-11-07 a 384x384, five-frame FP8-text attempt registered all 400 high-noise pixel-adapter targets and all 800 tensors, then the process-private guard stopped it at 12.37 GiB with 3.23 GiB free commit and 14.10 GiB free physical RAM. This was a guard stop, not proof of a CUDA or operating-system out-of-memory condition; no video frames were produced.

The optional `animation-q3-text` profile retains both Q3 A14B experts and both pixel-adapter stages but selects [city96/umt5-xxl-encoder-gguf](https://huggingface.co/city96/umt5-xxl-encoder-gguf/tree/b535255bee98c2b0a59ea7c0ae2dcd0c6657b3b7) revision `b535255bee98c2b0a59ea7c0ae2dcd0c6657b3b7`, file `umt5-xxl-encoder-Q3_K_S.gguf` (2,858,489,696 bytes; SHA-256 `f64f8d6dc4d8a24276df69d0ccea789aae686f7417950a41e6568c30cb478a5c`). Header inspection found a `t5encoder` architecture, T5 tokenizer metadata and a 256384x4096 embedding compatible with the pinned ComfyUI-GGUF loader. That loader dequantizes the embedding to FP16, so peak RAM savings cannot be inferred from file size alone. The model author recommends higher quantization for quality where resources permit. Its file downloaded and passed SHA-256 verification; the later Q2/Q3 mapped run completed with this encoder.

## Verification report

This report records checks performed on the local machine. A five-frame animation completed on the GPU with the mapped Q2/Q3 configuration described below; earlier configurations stopped at the memory guard.

Paths under `outputs/` refer to local test artifacts and are not included in the repository. The commands below can be used to produce new artifacts on a suitable machine.

### Environment and setup

- Windows 11; NVIDIA GeForce RTX 4070 SUPER, 12,282 MiB VRAM, driver 610.88; 32 GiB system RAM.
- `uv sync --locked --python 3.11` completed in `.venv`: PyTorch 2.8.0+cu128, Diffusers 0.35.2, Transformers 4.55.4, Accelerate 1.10.1 and PEFT 0.17.1. `pixcli doctor` confirmed CUDA availability and the GPU.
- `pixcli models verify --profile image` checked all 19 pinned files, including SDXL FP16 components, Pixel Art XL, and the fixed VAE; all hashes matched. `pixcli/model_manifest.json` contains exact paths, revisions, sizes, source URLs and digests.
- The separate pinned ComfyUI backend was installed. The initial CUDA 12.8 environment started successfully, but ComfyUI warns that CUDA 13 is required for NVIDIA 20-series and newer GPUs, so the backend lock was updated to PyTorch 2.12.1 with CUDA 13.0; its installation completed, and `uv pip check` reported all 87 installed backend packages compatible. `python scripts/check_backend.py` started it on localhost without models, confirmed registration of GGUF, PainterI2V and checked pixel-LoRA nodes, checked graph input names and connection types, and shut it down. After the CUDA 13 update, `python scripts/check_backend.py --gpu` confirmed startup on the RTX 4070 SUPER with the explicit low-VRAM flags and shut down cleanly. An initial run exposed a Windows child-process shutdown issue; a process-tree fix was added and the check then exited successfully.
- `pixcli models download --profile animation` completed for the original Q3-expert/FP8-text selection (now named `animation-q3-fp8`; the current `animation` default selects Q2/Q3). The seven original files total 23.22 GiB, with 30.49 GiB reserved including temporary space. All seven passed `pixcli models verify --profile animation`; inspection of the downloaded safetensors header found 800 BF16 tensors, comprising 400 A/B pairs at rank 256.

### Automated tests

`.\.venv\Scripts\python.exe -m pytest -q` passed 97 tests. They cover validation, offline missing models, hashes, mask preservation, image and sprite-sheet dimensions, timing, metadata, overwrite behavior, adapter and graph checks, and process-tree shutdown. ### Animation

An offline `animate` invocation before the model download completed exited with code 1 and named the missing high-noise checkpoint and the download/verification commands. On 2026-11-07, `.\scripts\smoke-animation.ps1` attempted a five-frame 384x384 job. The high-noise expert registered all 400 adapter target matrices and all 800 tensors with zero unmatched keys. The memory guard then stopped the backend at 12.37 GiB process private memory, 14.10 GiB free physical RAM and 3.23 GiB free commit; it produced no frames. A separate Q3 UMT5 encoder file was downloaded and passed SHA-256 verification. An explicit Q3-text/Q3-expert 384x384, five-frame attempt also registered the high adapter (400 targets, 800 tensors, zero unmatched) and stopped at 12.56 GiB private memory, 16.45 GiB available physical memory and 2.79 GiB free commit, before producing frames. Phase telemetry showed the text encoder had been released before expert loading. The same A14B experts in Q2_K format were then downloaded as a separate explicit candidate; both 5,300,957,696-byte files passed SHA-256 verification. All seven Q2/FP8 profile files and both Q2 experts passed hash verification. An explicit Q2-expert/Q3-text 384x384, five-frame run also registered the high adapter (400 targets, 800 tensors, zero unmatched), then stopped at 12.31 GiB private memory, 20.21 GiB available physical RAM and 1.27 GiB free commit. No frames were produced. Sampling cannot prevent every short memory spike. An explicit GPU-resident Q2-expert/FP8-text attempt then registered the high adapter (400 targets, 800 tensors, zero unmatched) and stopped before sampling at 12.00 GiB private memory, 20.04 GiB available physical RAM and 2.37 GiB free commit. No frames were produced. The mode was selected explicitly; no automatic fallback occurred.

The command `.\scripts\smoke-animation.ps1 -TextEncoder fp8 -ExpertQuant q2 -Preset gpu-resident -AdapterDevice cuda -OutputDirectory outputs/smoke/walk-q2-cuda-adapter` explicitly loaded the pixel adapter onto CUDA. The high expert again registered 400 targets and 800 tensors with zero unmatched; before sampling, the guard stopped at 12.56 GiB process private, 20.13 GiB physical available and 2.15 GiB free commit. The 12 GiB private cap and the 2 GiB minimum free-memory thresholds are sampled, so measurements can overshoot. A tiny safetensors file was independently loaded and compared on CPU and CUDA to check device selection; this does not prove full generation. See `outputs/diagnostics/q2-cuda-adapter.log` for the attempt.

Those earlier attempts did not reach the low-noise expert or produce frames. The measured stops did not establish that this combination was impossible on the hardware; the subsequent successful run is recorded below. The adapter, stage routing, GGUF candidate, memory constraints and uncertainty are documented in [animation research](#animation-compatibility-investigation). A bounded remote-header check with `.\.backend\.venv\Scripts\python.exe scripts/inspect_gguf_headers.py` matched all 400 adapter target names and logical shapes against each Q3 GGUF expert header. The runtime checks require 400 registered target matrices and 800 consumed adapter tensors for each expert, but header checks and a successful server startup do not prove the quantized end-to-end combination works. Those earlier attempts did not permit an assessment of flicker, identity drift, loop discontinuity or animation exports.

### Successful mapped animation run

On 2026-11-08, after applications were closed, the following job completed on the RTX 4070 SUPER. It used Q2_K experts, Q3_K_S text, the disk-mapped expert loader, and the CPU pixel adapter. It was submitted with offline mode; the pinned local ComfyUI server also started with its offline flag. This run was not instrumented to block all network connections.

```powershell
.\.venv\Scripts\pixcli.exe animate --input outputs/smoke/knight.png --prompt 'the knight walks in place, fixed camera' --out outputs/smoke/walk-mmap-q2 --seed 42 --preset low-vram --text-encoder q3 --expert-quant q2 --weight-storage mmap --max-private-gib 14 --min-free-commit-gib 2 --min-free-physical-gib 2 --inference-width 256 --inference-height 256 --frames 5 --fps 8 --pixel-width 96 --pixel-height 96 --offline
.\.venv\Scripts\python.exe scripts/verify_animation.py outputs/smoke/walk-mmap-q2
```

Both high- and low-noise stages reported 400 adapter targets, 800 tensors and zero unmatched. Export verification passed for five 96x96 frames, sprite-sheet coordinates and timing, GIF, MP4, and metadata. Model inference took 124.859 seconds; sampled peak backend process-private memory was 14,206,365,696 bytes (13.23 GiB), and sampled device-wide GPU usage peaked at 7,440,695,296 bytes (6.93 GiB). Free Windows commit was about 17.1 GiB before startup; phase logs report about 3.08 GiB remaining when the low expert was registered, but the run did not record the overall minimum. Limits are sampled and can be exceeded between checks. See `outputs/diagnostics/mmap-q2-retry.log` and `outputs/smoke/walk-mmap-q2/metadata.json`.

Visual inspection of the five-frame sprite sheet shows a recognizable knight with subtle changes, but no convincing walking cycle; the very short clip does not demonstrate seamless looping. The background and fine details vary between frames, and the pixel grid is not perfectly uniform. Q2 and Q3 quantization can affect quality. The run validates execution and exports for this configuration, not a guarantee of quality or success at higher resolutions and frame counts.

After making those settings the defaults, `.\.venv\Scripts\pixcli.exe animate --input outputs/smoke/knight.png --prompt 'the knight walks in place, fixed camera' --out outputs/smoke/walk-default --seed 42 --offline` also completed. The export verifier confirmed five 128x128 frames, 8 fps, the GIF, MP4 and sprite sheet, and complete coverage for both experts. The backend took 101.609 seconds, with 14,172,762,112 bytes peak sampled private memory and 7,460,618,240 bytes peak sampled device-wide GPU use. The result likewise shows only subtle movement rather than a clear walking cycle.

The mapped loader avoids the pinned GGUF patcher's eager detachment of offloaded mapped weights; it is a project-specific experimental change. A separate real-tensor CUDA probe used one Q2 expert matrix and both actual pixel and high-stage distillation LoRA pairs. It checked the patched result against independent dequantized calculation after cloning and low-VRAM loading, and checked that mapped bytes were unchanged. That probe covers one layer, not the full model.

A follow-up using the same quantization and memory guards at 384x384 with nine frames stopped at the commit-memory guard during the high-noise stage, before producing frames. The last sample showed 13.26 GiB process-private memory and 1.41 GiB free commit; this was below the configured 2 GiB reserve because the guard samples periodically. See `outputs/diagnostics/mmap-q2-9.log`. This failure shows why the small successful settings and memory headroom matter; it is not evidence of an intrinsic maximum resolution.
